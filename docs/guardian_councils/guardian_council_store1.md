# Guardian council: STORE-1 (the exact GF(17) store as the drive)

Question: answers fail at resolution (question -> entity + property, or -> another store), not storage. How do we make the exact store ultra-compact and the drive for fast, accurate answers, inside the paradigm (LUT not matmul, GF(17) digits, coordinates not numbers, PTEX pages, SSD streaming), and measure it honestly?

- **Architect**: one container of GF(17) digit pages holding every component: Huffman-cascade fact levels (A1 ribbon, one digit per cell), presence signatures, counts, qualifiers, codebooks, the name table and the text codec streams. Extend `crates/adam-torus` (generic digit rows instead of a fixed 6-digit id) rather than copying the ribbon; a new `crates/adam-store1` holds the builder, reader, parity check and a C-ABI reader for Python. The resolver is Python over that reader, reusing `wikifact.nrm`, its `WHEN`/`WHO`/`NOUN` tables, `cognition.qclass`/`isa`, the ConceptNet/WordNet readers and `amni/math`.
- **Sentinel**: pre-register gates first; the eval set is written by an agent that sees no repo code or eval data, decontaminated (6-gram) against all of `data/adam_t/eval/**`, split once, hash-locked, test scored once. The coverage audit of the locked E2E items is done by a separate agent and only its aggregate table is read by the resolver author. Parity is checked on every fact, label and name key, not a sample.
- **Scholar**: the information bound sets the target: H(value | property) is 9.4 bits for entity facts while the A1 table spends 38.5 bits; a 17-ary Huffman code reaches 10.1 bits, and an exact presence signature (H 9.3 bits per subject) replaces per-key fingerprints. Report bits per fact against both the entropy and the codebook bound.
- **Engineer**: CPU only (GPU belongs to another agent), `systemd-run --user --scope -p MemoryMax=12G -p CPUQuota=300% nice -n 15`, own Rust target dir deleted after, outputs under `data/store1/` (cap 15 GB), v3 left in place. Batch C-ABI calls keep Python overhead off the latency path.
- **Pathfinder**: order by value: resolver accuracy first (the measured bottleneck), then compaction with full parity, then latency, then the flag. Each lever is ablated on dev; things that do not pay (derivation rules, reverse index, fingerprints) are measured and reported rather than assumed.

Majority (5/5): Architect's layout, Sentinel's protocol, Scholar's bound-driven design, Engineer's resource rules, Pathfinder's order. No tie.
